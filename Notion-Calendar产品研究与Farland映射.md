# Notion Calendar research for Farland

This report analyzes only **Notion Calendar**, and uses two evidence bases: official Notion product/help materials for the product itself, and the current Farland miniapp repository for translation into Farland’s domain. Notion publicly positions Calendar as a place to keep “all of your commitments” together, combining work and life, built-in scheduling, menu-bar access, time-zone handling, and direct links to Notion docs and databases. Farland’s current MVP, by contrast, is a request-to-quote miniapp centered on `ride_requests`, shared `quote_invites`, a driver quick-quote page, and operator-side quote review/selection, with `task_description` as the main driver-visible request field and `internal_note` reserved for operators. citeturn31view0turn15view1turn37view0

## Core product mind

Notion Calendar wants the user to understand **time as an operating surface, not a passive record**. The product page does not describe the calendar merely as a place to store meetings; it describes a single place for “all of your commitments,” with scheduling, time-zone coordination, deadline visibility, and Notion workspace context all inside the same product. The key mental model is: **when you look at time, you should also see the work, the people, the constraints, and the next action attached to that time**. citeturn31view0

That mental model changes the relationship between **events, tasks, time blocks, collaboration, and context**. Events are not isolated calendar objects. They can become focus time, out-of-office, birthday events, availability slots, or database-backed work items with editable status properties. Notion databases with date properties can be pulled into the calendar; meeting notes and pages can be attached to events; scheduling links are created from the same environment rather than being exiled to a separate tool. The product is effectively training users to think: **time block first, attached work second, collaboration controls third, but all in the same frame**. citeturn32view0turn32view2turn32view3turn20view0

The collaboration model is equally important. Notion Calendar treats coordination overhead as a first-class UX problem. The official materials emphasize menu-bar meeting access, teammate calendars, drag-and-drop 1:1 creation, scheduling links, automatic conflict avoidance, and cross-calendar blocking. That means the product mind is not “calendar as storage”; it is **calendar as negotiation layer**: a place where users resolve availability, find overlap, and turn tentative timing into committed work with minimal back-and-forth. citeturn31view0turn23view0turn32view3turn32view4

For Farland, that mindset is directly relevant. Farland is also not selling a static record. It is coordinating an operational negotiation: a transportation request becomes a driver invitation, then driver quotes, then operator review, then selection or publication to the customer. The repo README explicitly describes the current flow as `ride_requests` → `quote_invites.token` → driver quick quote → `getQuoteInviteByToken` → `submitQuickQuote`, and states that `task_description` is the core driver-visible field while `internal_note` stays operator-only. That is already a time-and-context workflow; it just needs a clearer surface model. citeturn37view0

## UI information architecture

Notion Calendar’s documented IA is built around a **persistent center canvas with contextual side surfaces**. The main calendar grid is the temporal canvas. The **left sidebar** holds durable objects: connected calendar accounts, individual calendars, Notion workspaces, databases, teammate calendars, and scheduling links. The **right context panel** is where an item becomes editable in detail: location, privacy, status, participants, notes, calendar assignment, and database properties are all edited there. Separate **left-side panels** appear for calendar-specific upcoming events and Notion database list management, meaning the product frequently uses the left side for “collection view” and the right side for “item detail.” citeturn32view0turn25view5turn32view2turn26view5

This is not incidental structure. It reflects a strong hierarchy of attention. The grid answers **“when?”**. The left side answers **“which stream or object family am I working in?”**. The right side answers **“what exactly is this item, and what can I change right now?”**. That division lowers user confusion because time remains visually stable while object-specific complexity is deferred to panels. A user can keep the whole schedule in view while still editing one item deeply. citeturn32view0turn32view2turn25view5

Creation and editing entry points follow the same logic. Users can create an event by selecting a time slot in the grid, by pressing `+` inside a calendar-specific panel, or by using the mobile floating add button. Multi-day events are created by dragging across days. Team 1:1s can be created by dragging a teammate onto the grid. Database items can be dragged into the calendar from a list panel, then edited in-place. This means the UI does not force the user through one canonical “new item” form. Instead, it honors the context they are already in: **calendar-originated creation, panel-originated creation, and drag-originated creation all converge into the same editable object model**. citeturn32view0turn32view1turn23view0turn32view2

Notion’s settings architecture is also revealing. The app has explicit settings for calendar visibility, week start, time format, menu bar behavior, notifications, density, number of visible days, all-day collapsing, connected accounts, Notion workspaces, and default databases for meeting notes. That is a sign of a product that treats the same underlying calendar not as a single fixed view, but as a configurable **workspace shell** tuned to different cognitive preferences and working styles. citeturn24view0turn24view1turn24view6

Official public materials are much less explicit about loading and empty states than they are about panels, commands, and editing surfaces. The evidence we do have suggests that Notion tries to keep the **calendar canvas persistent** and lets emptiness live inside side panels or filtered collections, rather than replacing the whole app with large state screens. That matters for Farland: stability of the main operational surface is more important than theatrical state transitions. citeturn32view0turn32view2turn26view5

## User behavior logic

The **new event** flow is built to begin with time, not with form complexity. A user selects a slot, enters a title and details, optionally changes event type, adds participants and rooms, and sends the invite. If the event spans multiple days, they drag across days first and refine afterward. If they are starting from collaboration context instead of time, they can drag a teammate to create a 1:1; if they are starting from work context, they can drag a Notion database item into the grid. The behavior pattern is consistent: **pick the temporal anchor first, then enrich the object**. That reduces the psychological cost of starting. citeturn32view0turn32view1turn23view0turn32view2

The **event detail** flow is similarly lightweight. Clicking an event opens a right context panel where the user can manage location, privacy, busy/free status, event type, participants, optional attendees, RSVP notes, and calendar assignment. The product avoids deep page transitions for event detail; it prefers side-panel editing so the user never loses sight of surrounding time. That is especially important for calendar behavior, because editing a meeting almost always requires checking adjacent commitments at the same time. citeturn32view1turn25view5

The **time modification** flow is deliberately direct-manipulation-heavy. Users drag events to new times, drag across days to define multi-day events, drag multiple selected events together, drag teammates into time slots, drag database items into the calendar, and even drag time zones to reorder them. This reveals a key behavioral assumption: users who manage time frequently do not want to reopen structured forms for every small adjustment. Instead, Notion tries to let the grid itself behave like the editing instrument. citeturn25view0turn23view0turn32view2turn36view1

The **conflict-handling** model is also behaviorally strong. Scheduling links can avoid conflicts automatically as new events appear; calendar blocking can create either full-detail or “show as busy” blocks across calendars; merged events reduce duplicate RSVP friction; room conflicts surface as warnings in the calendar. Notion is solving conflicts at multiple levels: scheduling links prevent them upstream, blocking manages them across calendars, merging suppresses duplicate representations, and warnings catch resource issues late in the flow. citeturn26view0turn26view4turn32view4turn32view1

The **switch between calendar and other contexts** is handled through command access, side panels, and database/doc integration rather than by sending users to separate products. Users can open scheduling links from the left contextual area, use command search to show a Notion database or manipulate time zones, attach meeting notes/pages, and manage database items from a left list panel while still editing a selected item in the right panel. The behavioral logic is clear: **context switching still happens, but it happens inside one shell**. citeturn26view5turn36view0turn36view1turn21view0

Finally, the product supports **quick decisions and batch scan behavior** especially well. The menu bar previews upcoming meetings and supports joining them while the app is in the background; users can quickly scan a specific calendar’s upcoming items from the left sidebar; density and visible-day settings help compress or expand the visual scan; multiple events can be selected and shifted together. In other words, Notion Calendar acknowledges two modes: deep editing and fast operational triage. citeturn31view0turn24view1turn24view6turn25view0turn32view0

## Interaction design details

The most important interaction choice is that **drag is not decoration; it is the product’s grammar**. Drag defines multi-day events, moves single events, shifts multiple events, creates 1:1s from teammates, imports database items into time, reorders time zones, and edits database dates. Because these actions all reuse the same spatial metaphor, the product teaches one core behavior and then extends it across adjacent object types. That lowers learning cost for power users and shortens the path from intention to change. citeturn32view1turn25view0turn23view0turn32view2turn36view1

The shortcut system is equally intentional. Official docs surface `?` for the shortcut catalog, global shortcuts for menu-bar show/hide and joining meetings, `S` for scheduling, `O` or command search for showing Notion databases, `cmd/ctrl + K` for command access, and `Z` for time-zone travel. This does not just make the app “fast”; it creates a layered efficiency ladder. Novices can click. Intermediate users can right-click and drag. Advanced users can bypass both and jump directly to intent. citeturn32view5turn26view6turn36view0turn36view1

Hover and concealment are used to control visual density. Many actions are hidden until intent is signaled: hover a calendar name to change color or add a database, right-click to block or bulk-edit, use `•••` to copy or edit scheduling links, hover a database list item to reveal quick edit, right-click a teammate calendar to pin or remove it. The point is not aesthetic minimalism for its own sake. The point is that heavy operators need access to many functions without paying a perpetual visual tax for all of them. citeturn32view0turn25view0turn26view5turn36view0turn23view0

The side-panel model lowers modal friction. The right context panel lets users modify an object while preserving awareness of neighboring time. The left list panel for Notion databases lets them scan, create, and drag items without leaving the calendar. The menu bar offers another layer of ambient access for “join / glance / act” moments. These are not separate screens competing with one another; they are **graduated layers of commitment**, from ambient awareness to focused editing. citeturn24view1turn32view2turn31view0turn32view5

Density and hierarchy are adjustable rather than fixed. Users can change days displayed, collapse the all-day area, zoom interface scale, zoom calendar hours, change whether weekends or declined events are shown, and decide how much of an event appears in the menu bar. This matters because calendar work oscillates between **broad planning mode** and **fine-grained scheduling mode**. The UI lets the user choose whether they want temporal breadth, temporal precision, or reduced visual noise. citeturn24view0turn24view1turn24view6

A subtler but crucial detail is how Notion makes **permission and editability legible inside the UI**. Database items are only editable in Notion Calendar if the user has sufficient access; some properties are read-only; mobile editing is narrower than desktop/web; team features depend on Google Workspace management. The interaction lesson is that flexible surfaces still need clear capability boundaries. Otherwise users click into an object expecting agency and instead discover unexplained dead ends. citeturn21view0turn28view0turn23view0

## Implications for Farland

Farland’s current MVP already has the skeleton of a Notion-like operational model, but not yet the same surface clarity. The repo describes the core flow as operator-created `ride_requests`, a shared `quote_invites.token`, driver quick-quote access, `getQuoteInviteByToken`, and `submitQuickQuote`. The current create-request page captures only `service_type`, `service_date`, `driver_region`, `task_description`, `quote_deadline`, and `internal_note`. The current operator detail page shows request summary, task description, internal note, cancellation controls, and a quote list with a single “选择该司机” action. The driver page shows request basics, driver/vehicle info, and quote input. citeturn37view0 fileciteturn10file0L3-L3 fileciteturn11file0L3-L3 citeturn7view0 fileciteturn8file0L3-L3

That means the first transferable principle from Notion Calendar is **surface separation, not visual similarity**. Farland should not borrow Notion’s look; it should borrow its structural logic: a stable main operational surface, a right-side detail/editing zone, and a left-side or top-level filter/view layer. Right now, Farland’s create flow and detail flow depend too much on one large driver-facing `task_description` plus separate operator notes. The repo README even states that `task_description` is the core driver-visible field. That is workable for an MVP, but it forces too much of the business model into unstructured prose. citeturn37view0

The second transferable principle is **service-type-aware structure**. In the current code, `service_type` exists and is surfaced on the create-request page, request detail page, and driver quick-quote page, but the actual UI structure barely changes beyond labels and page title. For operators, this means `transfer` and `charter` still share nearly the same page shape and depend on free text to describe operational differences. For drivers, the title changes, but the information card is structurally the same. Notion Calendar’s lesson is that when objects differ in behavior, the UI should not just relabel them; it should **recompose the object summary** so the user can scan the right things first. fileciteturn10file0L3-L3 fileciteturn11file0L3-L3 citeturn7view0 fileciteturn8file0L3-L3 fileciteturn9file0L3-L3

The third principle is **status should behave like object state, not button clutter**. Notion’s side-panel model reduces action overload by making the currently selected object the place where state changes happen. In Farland, the operator detail page currently still renders a one-step selection CTA on each quote row, while the page JS already contains more advanced scaffolding for review, publish, reject, customer invite creation, and polling. That split is a warning sign: the business flow is becoming multi-stage, but the UI grammar is still single-stage. A Notion-derived answer would be to make quote state legible and progressive—reviewed, drafted, published, selected, rejected—so the page explains the workflow without forcing the operator to infer it from disparate buttons. citeturn7view0 fileciteturn12file0L3-L3

The fourth principle is **privacy by object design, not by afterthought**. Notion’s blocking feature explicitly allows either “include details” or “show as busy,” which is a strong example of privacy being part of the UI contract. Farland needs the same discipline. The current repo already does some of this correctly: `getQuoteInviteByToken` returns only a narrow request object plus driver/vehicle snapshots and existing quote summary; the driver page never receives customer phone, customer pricing, other driver quotes, margin, or `internal_note`; and the README explicitly says `internal_note` is operator-only and `openid` is always server-derived. This is the right pattern and should be extended: **driver-visible data should be a dedicated published summary object, not a filtered subset of operator objects**. fileciteturn18file0L3-L3 fileciteturn9file0L3-L3 citeturn37view0

One repo detail makes this especially important: the README says duplicate quote submissions should update the original quote, but the current driver flow actually locks the quote after submission and the cloud function returns `409` if the same driver resubmits. That discrepancy means the UI must be very explicit about what the driver can still do after submission. Notion Calendar is strong here because it makes editability and state transitions visible in-context. Farland should do the same, especially on quick-quote banners and operator-side quote-state labels. citeturn37view0 fileciteturn19file0L3-L3 fileciteturn9file0L3-L3

## Farland UI and UX recommendations

For the **operator create request page**, the best direct adaptation is a **progressive, service-type-aware form**. Keep the top segmented control for `transfer` / `charter`, but let it materially reorganize the rest of the page. For `transfer`, the first visible groups should be: service date/time, pickup, drop-off, flight/train or arrival context if relevant, passenger count, luggage, preferred vehicle, driver region, quote deadline, driver-facing brief, operator-only notes. For `charter`, the first visible groups should be: service date or date range, service window, city/base region, stop summary, passenger count, luggage, preferred vehicle class, driver region, quote deadline, driver-facing brief, operator-only notes. The current implementation already has the correct top-level switch but keeps almost everything else unchanged; the recommendation is to move critical structured fields out of `task_description` and leave the free-text field as a summary layer rather than the primary data carrier. fileciteturn10file0L3-L3 fileciteturn11file0L3-L3

For the **request list / dispatch view**, Farland should treat each request as a compact operational object, similar to how Notion treats calendar/database objects. A card or row should show: request number, service-type tag, primary time signal, primary route/window summary, region, quote count, deadline urgency, and one “next action” label. The current request hall already shows request number, tag, service type, date, region, preview text, quote count, invite count, and deadline. The improvement is to make the preview more structured and less prose-heavy: a transfer card should foreground route; a charter card should foreground service window and stop count. This reduces scan cost because operators can answer “what is this?” before opening detail. fileciteturn15file0L3-L3 fileciteturn16file0L3-L3

For the **operator detail page**, use a stable top summary and put mutable decision logic into a dedicated quote detail area. The first card should always show request identity, service type, date/time window, region, customer-facing trip summary, and operator-only note. The second region should be the quote rail, where each quote row shows driver snapshot, vehicle snapshot, quoted amount, submitted/updated time, and a single dominant next action based on status. Instead of showing many simultaneous buttons, use status-first transitions: `Received` → `Review`, `Reviewed` → `Create client option`, `Drafted` → `Publish`, `Published` → `Await customer`, `Customer selected` → `Confirm driver`, `Rejected` or `Cancelled` → historical only. The current page already has the request summary, cancellation panel, and quote list; it is the action grammar that now needs to be restructured. citeturn7view0 fileciteturn12file0L3-L3

For **quote status management**, I recommend an explicit Farland status vocabulary that is visible both in list cards and in detail rows: `New`, `Awaiting quotes`, `Quotes received`, `Under review`, `Draft prepared`, `Published to customer`, `Customer selected`, `Assigned`, `Cancelled`, `Expired`. This is intentionally broader than the repo’s current core statuses because Farland’s requested workflow already includes “review → draft → publish → revoke → confirm.” The user-behavior reason is simple: when workflows expand, users stop trusting unlabeled buttons and start scanning for predictable system states. Notion Calendar succeeds because each interaction surface makes the object’s current state legible before asking the user to act. citeturn31view0turn32view2turn24view1

For the **driver quick-quote page**, the biggest opportunity is a smarter first card. Right now the page shows a uniform “task information” block with request number, service type, service date, region, deadline, and `task_description`, followed by driver/vehicle and quote cards. A better design is to make the first card highly service-type-specific. A `transfer` quote card should show pickup, drop-off, service date/time, passengers, luggage, vehicle preference, and driver-facing rules like wait-time assumptions. A `charter` quote card should show service window, region/city, main itinerary summary, estimated hours or date span, passenger count, luggage, and vehicle preference. The pricing card should then ask the driver to quote **against a structured brief**, not against a single dense paragraph. This lowers the risk of omitted assumptions and improves price comparability for operators. fileciteturn8file0L3-L3 fileciteturn9file0L3-L3

On **copywriting and information priority**, Farland should explicitly rename the public/private split. Instead of “任务描述” plus “内部备注,” use labels that teach permission boundaries: `Driver-facing brief` and `Operator-only note`. On the driver page, the submit placeholder should ask for exactly the information Farland needs for downstream review: included items, excluded items, waiting assumptions, overtime rule, toll/parking handling. That matches Notion Calendar’s habit of embedding next-step context directly in the object rather than expecting users to mentally reconstruct business rules later. fileciteturn10file0L3-L3 fileciteturn8file0L3-L3 citeturn32view0turn21view0

The driver quick-quote API should continue to whitelist only the fields necessary for quoting. For **mobile**, resist deep page nesting. Notion Calendar’s strength on mobile is fast glanceability and quick-add behavior, while more detailed editing is stronger on desktop/web. Dense form editing and complex multi-stage quote publishing will likely be better on a desktop/back-office surface or a carefully simplified mobile drawer/bottom-sheet pattern. citeturn31view0turn32view0turn28view0

## Design patterns that Farland should not adopt

Farland should **not** adopt Notion Calendar’s heavy dependence on shortcuts and command-driven expert UX as a primary strategy. Notion can rely on command search, global shortcuts, and menu-bar flows because a large share of its behavior target is desktop knowledge work. Farland’s operator workflow may benefit from fast actions on desktop later, but the driver quick-quote flow is a miniapp/mobile context first. If Farland over-optimizes for hidden power features too early, discoverability will collapse for the users who matter most. citeturn32view5turn31view0

Farland should also avoid making **drag** the primary mechanism for critical operational edits in its current phase. In Notion Calendar, drag is safe because many changes are low-risk temporal adjustments to familiar objects. In Farland, changing a pickup time, route assumption, or quote publication state can have commercial consequences. Direct manipulation is useful for low-risk schedule placement in a dispatch view, but not as the only or default way to edit high-stakes transport details. citeturn25view0turn32view2turn36view1

Another pattern to avoid is **over-flexible object modeling too early**. Notion Calendar supports multiple accounts, multiple workspaces, multiple databases, database views, teammate calendars, scheduling links, time zones, menu bar layers, and several event types inside one shell. That flexibility is powerful, but Farland does not need that level of user-configurable object sprawl yet. In the current Farland stage, too much configurability would raise support cost, create permission ambiguity, and make the core request-to-quote flow harder to learn. citeturn15view1turn21view0turn24view1

Farland should not adopt **implicit automation that hides audit logic**. In Notion Calendar, automatic event merging, auto-blocking, and conflict avoidance are excellent because the domain cost of small automation errors is relatively low and users can usually recover quickly. In Farland, a hidden merge, silent reassignment, or automatic publication step would create trust and accountability problems. Every transition that affects quote visibility, customer communication, or final driver selection should remain explicit, stateful, and auditable. citeturn32view1turn32view4turn26view0

Finally, Farland should not copy Notion Calendar’s **information density** on day one. Notion compresses many action layers because its audience manages calendars continuously and benefits from a dense shell. Farland operators absolutely need a high-information surface, but the information itself is different: routing, passenger/luggage assumptions, vehicle fit, quote count, review state, customer publication state, and privacy boundaries. If Farland copies density without reordering the content around operational decisions, the result will be clutter rather than speed. citeturn24view1turn24view6turn31view0
